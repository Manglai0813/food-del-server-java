# プロジェクト移行概要

## 概要

Food Delivery Platform のバックエンドサーバーを TypeScript (Bun + Express) から Java 21 + Spring Boot 3 へ移行するプロジェクトです。

## 移行の目的

- **エンタープライズ対応**: Java エコシステムの成熟度と安定性を活用
- **型安全性の強化**: Java の強力な型システムによる安全性向上
- **チーム拡張性**: Java 開発者の採用と育成が容易
- **長期保守性**: エンタープライズ環境での運用実績

## 技術スタック対応表

| 現行技術 | 移行先技術 | 備考 |
|---------|----------|------|
| Bun + Express | Spring Boot 3 | Web フレームワーク |
| TypeScript | Java 21 | プログラミング言語 |
| Prisma ORM | Spring Data JPA + Hibernate | ORM 層 |
| PostgreSQL | PostgreSQL | データベース（変更なし） |
| JWT (jsonwebtoken) | Spring Security + JWT | 認証・認可 |
| Zod | Bean Validation (Jakarta) | 入力検証 |
| bcryptjs | BCryptPasswordEncoder | パスワードハッシュ化 |
| express-rate-limit | Spring Boot Actuator + Resilience4j | レート制限 |
| multer | MultipartFile | ファイルアップロード |

## アーキテクチャ対応

### 現行アーキテクチャ

```
Routes → Controllers → Services → Prisma
```

### 移行後アーキテクチャ

```
Controller → Service → Repository → JPA Entity
```

### 層の対応関係

| 現行 | 移行後 | 説明 |
|-----|--------|------|
| Routes | Controller | ルーティング定義 |
| Controllers | Controller | HTTP リクエスト処理 |
| Services | Service | ビジネスロジック |
| Prisma | Repository + Entity | データアクセス |
| Middleware | Filter + Interceptor + Aspect | 横断的関心事 |
| Types | Entity + DTO | 型定義 |
| Errors | Exception | エラーハンドリング |

## プロジェクト構造（細粒度設計）

```

├── repository/              # データアクセス層
├── entity/                  # JPA エンティティクラス

│   └── response/           # レスポンス DTO
├── mapper/                  # Entity-DTO 変換器
├── security/                # セキュリティモジュール
│   ├── jwt/                # JWT 関連
│   └── filter/             # セキュリティフィルター
├── exception/               # 例外処理
│   ├── handler/            # 例外ハンドラー
│   └── custom/             # カスタム例外クラス
├── config/                  # 設定クラス
│   ├── security/           # セキュリティ設定
│   ├── database/           # データベース設定

│   └── codes/               # エラーコード

```

## 主要機能の移行方針

### 1. 認証・認可システム

- **JWT トークン管理**: Spring Security の JWT サポートを活用
- **アクセストークンとリフレッシュトークン**: 二種類のトークンによる認証
- **ロールベースアクセス制御**: `@PreAuthorize` アノテーションで実装
- **パスワードハッシュ化**: BCryptPasswordEncoder による安全な保存
- **トークンリフレッシュ**: Refresh Token の管理と検証
- **ログアウト機能**: トークンの無効化処理

### 2. ユーザー管理システム

- **ユーザー登録**: メールアドレス重複チェック、パスワード強度検証
- **プロフィール管理**: ユーザー情報の取得・更新
- **パスワード変更**: セキュアなパスワード変更機能
- **ユーザー検索**: メールアドレスによるユーザー検索

### 3. 商品管理システム

- **商品 CRUD 操作**: 商品の作成・読み取り・更新・削除
- **商品検索・フィルタリング**: カテゴリ、ステータス、キーワード検索
- **公開商品一覧**: ステータスが有効な商品のみ取得
- **注目商品取得**: 特定条件による商品抽出
- **カテゴリ別商品取得**: カテゴリに基づく商品フィルタリング
- **ページネーション**: 大量データの効率的な取得

### 4. カテゴリ管理システム

- **カテゴリ CRUD 操作**: カテゴリの作成・読み取り・更新・削除
- **アクティブカテゴリ取得**: 有効なカテゴリのみ取得
- **カテゴリ別商品取得**: カテゴリに紐づく商品一覧
- **カテゴリステータス管理**: カテゴリの有効/無効切り替え

### 5. ショッピングカートシステム

- **永続的なカート機能**: ユーザーごとのカート管理
- **商品追加・削除**: カートへの商品追加と削除
- **数量更新**: カート内商品の数量変更
- **在庫予約システム**: カート追加時の在庫予約機能
- **カートサマリー計算**: 合計金額、商品数の計算
- **カートクリア**: カート内全商品の削除
- **チェックアウト機能**: カートから注文への変換

### 6. 在庫管理システム

- **在庫更新**: 在庫の追加・減算操作
- **楽観的ロック**: JPA の `@Version` アノテーションで自動実装
- **悲観的ロック**: `@Lock(LockModeType.PESSIMISTIC_WRITE)` で実装
- **在庫予約機能**: カート追加時の在庫予約
- **予約解除機能**: カート削除時の予約解除
- **在庫確定処理**: 注文確定時の在庫減算
- **在庫履歴記録**: すべての在庫変更の履歴管理
- **在庫情報取得**: 現在在庫、予約在庫、利用可能在庫の取得

### 7. 注文処理システム

- **注文作成**: カートから注文への変換
- **トランザクション管理**: `@Transactional` アノテーションで宣言的トランザクション
- **在庫確定処理**: 注文作成時の在庫減算をトランザクション内で実行
- **注文ステータス管理**: ステータス履歴の記録
- **注文一覧取得**: ユーザー別、管理者用の注文一覧
- **注文詳細取得**: 注文情報と注文アイテムの詳細
- **注文キャンセル**: 注文のキャンセル処理
- **注文統計**: 管理者向けの注文統計情報
- **注文履歴**: 注文ステータス変更履歴の取得

### 8. ファイル管理システム

- **画像アップロード**: 商品画像のアップロード機能
- **ファイル検証**: ファイルタイプ、サイズの検証
- **ファイルストレージ**: 公開/非公開ファイルの管理
- **ファイルアクセス制御**: 認証に基づくファイルアクセス制御
- **デフォルト画像**: 画像未設定時のデフォルト画像提供

### 9. セキュリティ機能

- **レート制限**: API 呼び出し頻度の制限
- **リクエストサイズ制限**: リクエストボディサイズの制限
- **セキュリティヘッダー**: Helmet 相当のセキュリティヘッダー設定
- **CORS 設定**: クロスオリジンリクエストの制御
- **入力バリデーション**: Bean Validation による厳格な検証
- **リクエストタイムアウト**: 長時間実行リクエストのタイムアウト制御
- **リクエスト監視**: リクエストのログ記録と監視

### 10. 統一レスポンス形式

- **ApiResponse クラス**: すべての API レスポンスを統一形式で返却
- **グローバル例外処理**: `@ControllerAdvice` で統一的なエラーハンドリング
- **ページネーション対応**: PaginatedResponse クラスで実装
- **エラーコード管理**: 統一的なエラーコード体系

## 主要な設計決定

### 1. 統一レスポンス形式の採用

すべての API レスポンスを `ApiResponse<T>` 形式で統一し、既存の TypeScript フロントエンドとの互換性を維持します。

### 2. 細粒度プロジェクト構造

機能ごとに明確に分離された構造を採用し、保守性と拡張性を向上させます。

### 3. サービスインターフェースの採用

コアビジネスロジックについてはサービスインターフェースを定義し、テスト容易性と拡張性を確保します。

### 4. グローバル例外処理

`@ControllerAdvice` を使用した統一的な例外処理により、エラーハンドリングの一貫性を保ちます。

## 互換性の維持

- **API エンドポイント**: 既存のエンドポイントパスを維持
- **レスポンス形式**: ApiResponse 形式を維持
- **認証方式**: JWT トークンベース認証を維持
- **データベーススキーマ**: 既存の Prisma スキーマを JPA エンティティに変換
