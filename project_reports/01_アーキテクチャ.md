## 1. プロジェクト概要

### 1.1 プロジェクト名

**Food Delivery Platform Backend** (フードデリバリープラットフォーム)

### 1.2 プロジェクト説明

Spring Boot 3をベースとした現代的なフードデリバリープラットフォームのバックエンドシステムです。標準的な三層アーキテクチャを採用し、ユーザー認証、商品管理、カート、注文処理などのコア機能を実装しています。

### 1.3 コア機能

- ✅ **JWT認証・認可** - トークンベースのステートレス認証
- ✅ **在庫予約メカニズム** - 過剰販売を防ぐ並行制御
- ✅ **ソフトデリート設計** - 履歴データの保持
- ✅ **楽観的ロック + 悲観的ロック** - 多層並行制御
- ✅ **統一例外処理** - グローバル例外インターセプト
- ✅ **Swagger APIドキュメント** - 自動生成インターフェースドキュメント
- ✅ **MapStructマッピング** - 自動化DTOコンバージョン

## 5. デザインパターン

### 5.1 DTOパターン (Data Transfer Object)

**目的**: 内部エンティティと外部インターフェースの分離

```java
// 内部エンティティ
@Entity
public class User {
    private Integer id;
    private String password;  // 機密情報
    // ...
}

// 外部レスポンスDTO
public class UserResponse {
    private Integer id;
    // passwordは含まない
}
```

**利点**:

- 機密情報の隠蔽
- ネットワーク転送データ量の削減
- 内部構造と外部インターフェースの分離

### 5.2 Repositoryパターン

**目的**: データアクセスロジックのカプセル化

```java
public interface UserRepository extends JpaRepository<User, Integer> {
    Optional<User> findByEmail(String email);
}
```

**利点**:

- 統一されたデータアクセスインターフェース
- データソースの切り替えが容易
- テストの簡素化

### 5.3 Service層パターン

**目的**: ビジネスロジックのカプセル化

```java
@Service
public class UserServiceImpl implements UserService {
    // ビジネスロジック実装
}
```

**利点**:

- ビジネスロジックの集中管理
- トランザクション制御
- 再利用性の向上

### 5.4 Builderパターン

**目的**: オブジェクト生成の簡素化

```java
@Builder
public class ApiResponse<T> {
    private boolean success;
    private T data;
    private String message;
}

// 使用例
ApiResponse.builder()
    .success(true)
    .data(user)
    .message("成功")
    .build();
```

### 5.5 Strategyパターン（潜在的）

**適用シーン**: 支払い方法、配送方法など

## 6. データフロー

### 6.1 リクエスト処理フロー

```
ユーザーリクエスト
    │
    ▼
┌─────────────────┐
│ Security Filter │ ← JWT検証
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Controller    │ ← リクエスト受信、パラメータ検証
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Mapper (DTO)   │ ← Request DTO → Entity
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│    Service      │ ← ビジネスロジック処理
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Repository    │ ← データベース操作
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│    Database     │
└────────┬────────┘
         │
         ▼ (戻りパス)
┌─────────────────┐
│  Mapper (DTO)   │ ← Entity → Response DTO
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Controller    │ ← ApiResponseでラップ
└────────┬────────┘
         │
         ▼
    JSONを返却
```

### 6.2 例外処理フロー

```
例外発生
    │
    ▼
┌──────────────────────┐
│ GlobalExceptionHandler│
└──────────┬───────────┘
           │
           ├─ BusinessException → ビジネスエラー
           ├─ ValidationException → パラメータエラー
           └─ Exception → システムエラー
           │
           ▼
    統一ApiResponse形式
           │
           ▼
     クライアントに返却
```

## 7. 主要技術決定

### 7.1 なぜPostgreSQLを選択？

- ✅ 強力なACIDサポート
- ✅ 豊富なデータ型
- ✅ 優れた並行性能
- ✅ オープンソース・無料

### 7.2 なぜJWTを使用？

- ✅ ステートレス認証
- ✅ クロスドメインサポート
- ✅ モバイルフレンドリー
- ✅ 高い拡張性

### 7.3 なぜソフトデリートを採用？

- ✅ 履歴データの保持
- ✅ データ復旧可能
- ✅ 監査追跡
- ✅ ビジネス要件に適合

### 7.4 なぜMapStructを使用？

- ✅ コンパイル時コード生成（高性能）
- ✅ 型安全
- ✅ 手書きコードの削減
- ✅ メンテナンス容易

## 8. パフォーマンス最適化戦略

### 8.1 データベース層

- **コネクションプール**: HikariCP（高性能）
- **インデックス**: 主要フィールドにインデックス作成
- **ページネーション**: 全テーブルスキャン回避
- **遅延ロード**: JPA関連の遅延ロード

### 8.2 アプリケーション層

- **キャッシュ**: Redisでホットデータをキャッシュ
- **非同期処理**: 非クリティカルな業務の非同期化
- **バッチ操作**: データベースラウンドトリップの削減

### 8.3 並行制御

- **楽観的ロック**: `@Version`フィールド
- **悲観的ロック**: `PESSIMISTIC_WRITE`
- **在庫予約**: 過剰販売防止
